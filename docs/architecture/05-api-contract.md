# POS Platform — API Contract v1

**Status:** Draft for Architecture Lock
**Version:** 1.0
**Architecture:** Modular Monolith, API-first, Event-ready
**Backend target:** Go
**Database:** PostgreSQL
**Primary clients:** POS, Admin, Backoffice, future Ecommerce/Mobile/Dealer

---

## 1. Purpose

API Contract v1 defines the stable boundary between clients and the POS Platform domain modules before Go implementation begins.

The contract is intentionally command-oriented for business transactions. CRUD endpoints are used only for master/configuration resources where appropriate.

The API must preserve:

- tenant isolation
- company/store/warehouse/terminal scope
- RBAC and permission checks
- idempotency for financial/business commands
- optimistic concurrency where applicable
- deterministic state transitions
- auditability
- transactional outbox/event publication
- ERP integration independence
- backward-compatible evolution

---

# 2. API Principles

## 2.1 Base URL

Production example:

`https://api.example.com/api/v1`

All public endpoints are versioned under `/api/v1`.

Versioning is URL-based for major API contracts. Minor backward-compatible changes do not require a new major version.

## 2.2 Resource naming

Use plural nouns for query resources:

- `/products`
- `/customers`
- `/sales/orders`
- `/payments`
- `/inventory/stocks`

Use explicit commands for state-changing business operations:

- `/sales/orders/{id}/confirm`
- `/sales/orders/{id}/void`
- `/payments/{id}/capture`
- `/payments/{id}/refund`
- `/inventory/adjustments/{id}/approve`

Avoid generic:

`PATCH /sales/orders/{id}`

for critical state transitions.

## 2.3 HTTP methods

| Method | Usage |
|---|---|
| GET | Query/read |
| POST | Create or execute command |
| PUT | Full replacement where truly required |
| PATCH | Non-critical partial update/configuration |
| DELETE | Rare; generally master-data deactivation instead |

Transactional business records should normally never be physically deleted through API.

## 2.4 Content type

Request/response:

`application/json`

Future binary upload endpoints may use `multipart/form-data`.

## 2.5 IDs

Public resource identifiers use UUID.

Example:

`01J...` is acceptable only if the implementation standardizes ULID; otherwise use UUID consistently.

Recommended v1: UUID v4 generated server-side.

Business document numbers are separate from technical IDs:

- technical ID: UUID
- business number: `POS-JKT01-20261006-000123`

Clients must not generate business document numbers.

# 3. Authentication

Recommended authentication model:

- access token: short-lived JWT or opaque token
- refresh token: rotating, hashed at rest
- MFA for privileged users
- session bound to user/device where appropriate

Header:

```http
Authorization: Bearer <access-token>
```

Recommended additional headers:

```http
X-Request-ID: <client-generated-or-server-generated-id>
X-Idempotency-Key: <unique-key>
If-Match: <version>
```

`X-Request-ID` is optional for clients but always generated by the API if absent.

The request ID must propagate to:

- application logs
- audit log
- outbox metadata
- integration delivery logs
- downstream requests where supported

# 4. Tenant and Scope Context

The API must derive authorization context from the authenticated identity and server-side scope.

Client-provided `tenant_id` must NOT be trusted as an authorization mechanism.

Possible context:

```json
{
  "tenant_id": "uuid",
  "company_id": "uuid",
  "region_id": "uuid",
  "store_id": "uuid",
  "warehouse_id": "uuid",
  "terminal_id": "uuid",
  "user_id": "uuid"
}
```

A POS terminal may provide `terminal_id`, but the server must verify that:

1. terminal belongs to the authenticated tenant/company/store;
2. user has access to that store/terminal;
3. terminal is active;
4. terminal is not assigned to another incompatible session.

The API must establish database transaction context using transaction-local settings before tenant-aware queries.

Example conceptually:

```sql
SET LOCAL app.tenant_id = '...';
SET LOCAL app.user_id = '...';
SET LOCAL app.store_id = '...';
```

Never use a pooled database connection with stale tenant context.

# 7. Standard Error Contract

All errors use:

```json
{
  "error": {
    "code": "SALES_ORDER_STATE_INVALID",
    "message": "Sales order cannot be voided in its current state.",
    "details": {},
    "request_id": "uuid"
  }
}
```

HTTP status mapping:

| HTTP | Meaning |
|---:|---|
| 400 | Invalid request format/business input |
| 401 | Authentication required/invalid |
| 403 | Permission/scope denied |
| 404 | Resource not found or intentionally hidden |
| 409 | State/concurrency/idempotency conflict |
| 422 | Semantically invalid business data |
| 429 | Rate limit |
| 500 | Unexpected internal error |
| 502 | Upstream provider failure |
| 503 | Temporary service unavailable |

Never expose:

- SQL errors
- stack traces
- database table names
- internal credentials
- provider secrets
- raw card data
- JWT/refresh tokens

# 8. Idempotency Contract

Required for commands that may create financial/business side effects.

At minimum:

- create sale
- confirm sale
- payment creation
- payment capture/charge
- refund
- stock adjustment posting
- stock transfer posting
- voucher redemption
- loyalty redemption
- external webhook processing

Header:

```http
X-Idempotency-Key: POS-SESSION-123-000456
```

Server stores:

```text
tenant_id
key
operation
request_hash
status
response_status
response_body/reference
created_at
expires_at
```

The same key with a different request hash must return conflict.

Recommended response:

`409 IDEMPOTENCY_KEY_REUSED_WITH_DIFFERENT_REQUEST`

The same key with the same request must return the original result rather than execute the command again.

# 9. Optimistic Concurrency

Resources with user-editable versions may expose:

```json
{
  "version": 7
}
```

Update may require:

```http
If-Match: 7
```

If the stored version changed:

`409 RESOURCE_VERSION_CONFLICT`

Critical stock/payment state transitions should use database locking/state-machine logic rather than relying solely on HTTP ETags.

# 27. API State Machines

## Sales Order

Recommended baseline:

```text
DRAFT
  ↓
CONFIRMED
  ↓
COMPLETED

DRAFT → CANCELLED
CONFIRMED → CANCELLED
COMPLETED → VOIDED
COMPLETED → REFUND_PENDING
REFUND_PENDING → REFUNDED
```

Exact transitions are domain-configurable but must be explicit.

## Payment

```text
PENDING
  ↓
PROCESSING
  ├→ SUCCESS
  ├→ FAILED
  └→ CANCELLED

SUCCESS → REFUND_PENDING → REFUNDED
```

Provider callbacks must obey the same state machine.

## Inventory Reservation

```text
ACTIVE
 ├→ RELEASED
 ├→ EXPIRED
 └→ CONSUMED
```

## POS Session

```text
OPEN → ACTIVE → CLOSING → CLOSED
```

No arbitrary state update.

# 28. Command Transaction Boundary

A critical command should follow:

```text
HTTP request
    ↓
Authentication
    ↓
Authorization/scope
    ↓
Validation
    ↓
Domain command
    ↓
DB transaction
    ├─ state mutation
    ├─ immutable ledger/history
    ├─ audit
    └─ outbox
    ↓
COMMIT
    ↓
async integration/event delivery
    ↓
HTTP response
```

External provider calls must normally happen outside the core transaction.

Where a provider requires a synchronous call, use an explicit payment state such as `PROCESSING` and design retry/reconciliation around it.

# 30. API Security Rules

Mandatory:

- TLS only
- authentication on protected endpoints
- authorization on every protected command
- tenant isolation
- scope enforcement
- rate limiting on authentication and public-sensitive endpoints
- request validation
- payload size limits
- secure headers
- structured logging
- correlation ID
- audit critical actions

# 31. POS-Specific Performance Requirements

POS lookup endpoints should be optimized for low latency.

Targets for initial architecture:

| Endpoint type | Target |
|---|---:|
| Barcode/product lookup | < 150 ms p95 under normal load |
| Customer lookup | < 250 ms p95 |
| Price/promotion evaluation | < 300 ms p95 for normal carts |
| Sale creation | < 500 ms p95 excluding external payment provider |
| Payment provider operation | Provider dependent |
| Stock availability query | < 200 ms p95 |

These are engineering targets, not SLA guarantees. Validate with load tests.

Use Redis only where caching provides measurable benefit. PostgreSQL remains source of truth for transactional state.

# 32. Offline POS Consideration

Offline POS is not part of the first implementation unless explicitly required, but API v1 must not prevent it.

Future offline synchronization will require:

- device identity
- local sequence
- idempotency key
- event timestamp
- conflict policy
- server authority rules
- duplicate detection

Do not attempt to solve offline inventory consistency by allowing clients to bypass server stock rules.

# 34. Webhook Security Contract

For every provider webhook:

1. validate signature
2. validate timestamp/replay window where supported
3. validate provider/event identity
4. persist raw provider event only if permitted and sanitized
5. deduplicate provider event ID
6. respond safely
7. process asynchronously
8. update domain state through command/service
9. write audit/event

Webhook endpoint must not accept arbitrary internal status changes.

```text
?page_size=50&cursor=...
```

Allowed sort fields must be whitelisted.

Never interpolate client-provided SQL fragments.

Example:

`sort=-created_at,business_number`

must be translated from an allowlisted field map.

Date filters use ISO 8601 timestamps.

Example:

`from=2026-10-01T00:00:00+07:00`

---

# 38. Money Contract

Money must never be represented as floating point.

Recommended JSON representation:

```json
{
  "amount": 1250000,
  "currency": "IDR"
}
```

For internal Go code use an integer minor-unit representation or decimal type according to currency rules.

If IDR is treated as zero-decimal, `1250000` means IDR 1,250,000.

Rounding rules must be centralized in the money/tax calculation domain.

---

# 39. Date/Time Contract

API timestamps use ISO 8601 with timezone/offset or UTC.

Example:

`2026-10-06T02:00:00Z`

Database timestamps should use `timestamptz`.

Business timezone is configuration, not hardcoded throughout application code.

# 42. Rules Against Architecture Drift

The following are prohibited without ADR:

1. adding direct cross-domain repository access;
2. exposing internal DB tables as public API;
3. adding provider-specific payment logic to Sales;
4. adding SAP-specific fields directly into Sales core entities;
5. bypassing audit for critical commands;
6. bypassing idempotency for financial commands;
7. adding arbitrary state-update endpoints;
8. allowing clients to control tenant context;
9. making external API calls inside long DB transactions;
10. changing event contracts without versioning.

Architecture changes require an ADR.

# 43. Initial API Acceptance Criteria

API Contract v1 is accepted only when:

- [ ] Every protected endpoint has authentication requirements.
- [ ] Every command has permission requirements.
- [ ] Store/warehouse/terminal scope is enforced server-side.
- [ ] Tenant ID is never trusted from client input for authorization.
- [ ] Critical commands have idempotency strategy.
- [ ] Critical state transitions are explicit.
- [ ] Sales cannot be voided by arbitrary PATCH.
- [ ] Payment cannot be duplicated by retry.
- [ ] Webhooks are signature-verified and deduplicated.
- [ ] Inventory mutation is transactional and concurrency-safe.
- [ ] Voucher redemption is atomic.
- [ ] Loyalty balance is ledger-derived.
- [ ] Audit is generated for critical business actions.
- [ ] Sensitive information is excluded from logs.
- [ ] ERP calls are asynchronous/retryable.
- [ ] Error contract is standardized.
- [ ] Request IDs propagate through logs/audit/events.
- [ ] OpenAPI can be generated from the contract.
- [ ] API tests cover authorization, idempotency, concurrency and state transitions.
